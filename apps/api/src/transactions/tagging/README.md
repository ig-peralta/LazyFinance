# Tag decisions and rules

Tags remain a single optional classification per movement. `transaction.tag_decision_origin` records *why* `tag_id` has its value: `unreviewed` + null means nobody has decided, `manual` + null means the user deliberately chose no tag, and `manual`/`rule` + a tag identifies the owner of a positive decision. `tag_rule_id` identifies an applied rule. Changes append a `tag_decision_event` for traceability; older tagged rows are backfilled as manual so later rules cannot overwrite them. Re-running the demo seed does not reset existing tag decisions.

`TaggingService` checks the authenticated user's ownership of the transaction, tag, rule, and optionally scoped account. It does not confirm income or determine whether a movement is internal. Users can assign or intentionally clear a tag through `PUT /transactions/:id/tag` (`{ "tagId": "uuid-or-null" }`), or remove their decision with `DELETE /transactions/:id/tag-decision`. Active tags are listed/created at `GET`/`POST /tags`.

Rule inputs use exact normalized merchant or description text, direction, optional owned account, tag, and priority. `POST /tag-rules` defaults to suggestion-only; `GET /transactions/:id/tag-suggestions` returns owned candidates with a reason and confidence. Description matches are suggestions only. An explicit `autoApply: true` on a structured merchant rule records approval; it applies only to confirmed non-internal movements without a manual decision. Unknown internal status remains suggestion-only. Tied top-ranked rules pointing to different tags do not auto-apply. `PUT /tag-rules/:id` replaces a rule and `POST /tag-rules/:id/archive` disables it for future matching; existing historical assignments are retained until their provider facts change or the user chooses otherwise. `POST /tag-rules/:id/apply?after=<transaction-uuid>` explicitly backfills up to 1000 eligible existing movements at a time and returns `nextCursor` for the next page.

During provider ingestion, manual tag/no-tag decisions always win. A provider correction re-evaluates only a rule-owned tag; if its match disappears, the rule-owned tag is cleared and a history event is recorded. Removed or provider-conflicted movements are never automatically tagged. This tagging decision is independent of a confirmed income receipt and of internal-movement assessment. The recent-movement read exposes tag provenance and review status so clients can distinguish an intentionally untagged movement from one awaiting a decision.
